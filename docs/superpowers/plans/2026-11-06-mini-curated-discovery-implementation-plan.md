# Mini Curated Discovery Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Implementation is a later, separately authorised stage; this document does not authorise commits, migrations, remote writes or deployment.

**Goal:** Add an optional regional Discovery embed that recommends curated services for the senior's entered postal code, with a left directory, right map and home-SR enquiry routing, while preserving ordinary Discovery and compact embeds.

**Architecture:** Add an independent regional page, guest API and framing handler. A revisioned owner document publishes an immutable curated service catalogue independently of its pins; each guest request applies current public permissions, authoritative postal coverage and approved contact rules. Reuse the map renderer through two small opt-in seams whose defaults preserve existing callers; provide a separate read-only detail panel and selection state machine.

**Tech Stack:** Existing React/JavaScript, Leaflet, Pages Functions, Hono Worker API, Drizzle/Postgres, Node test runner and existing browser harness. No new package dependency is planned.

**Spec:** `docs/superpowers/specs/2026-11-06-regional-discovery-embed-design.md`, reviewed design SHA-256 `7256bbfdd75eb3b709f767e4f96e8fba094869343355e019ff97f88fc16abd53`.

## Review Focus

1. Zero/multiple/unavailable real-SR matches, or only Singapore national fallback: retain browsing, coverage-unconfirmed, never false outside-region (Task 3).
2. Postal edit/Clear/Retry/token change races an older response: immediately retire old badges/distance/location contacts; accept one current full payload. A service-filter change prunes selection while retaining valid postal context (Task 9).
3. Selected venue withdrawal, same-pin services and intentional unplotted entries: never widen scope or transfer recommendations/contacts (Tasks 5, 8).
4. Changed original email, expired agreement, withdrawn grant or one missing registry field: suppress that field without silent recipient fallback or permission bypass (Task 4).
5. Keyboard/coarse-pointer visitors, all-unmapped results, short height and 200% text: every service remains reachable, no hover-only action or empty-bounds zoom (Tasks 8, 10).

| Entry | `{entryKey:'hard:<id>'|'soft:<id>',publishedOrder:number,name:string,categoryKey:string,categoryLabel:string,shortDescription:string|null,description:string|null,addressText:string|null,websiteUrl:string|null,logoUrl:string|null,pinPlaceKeys:string[],placement:'plotted'|'intentionally-unplotted'|'coordinates-unavailable',recommended:boolean,distanceMeters:number|null,contacts:{email:Contact,phone:Contact}}`. Never resource-row rest-spread. All protected website/media/text fields retain live public approval. |
| Contact | `{status:'available'|'hidden'|'needs-postal'|'temporarily-unavailable',appliesTo:'service'|'entered-location',label?:string,value?:string,href?:string}`. Emit destination/label/href only when available. |
| Public category / pin | `PublicCategory={key:string,label:string}`; `PublicPin={placeKey:string,latitude:number,longitude:number,entryKeys:string[]}`. Safe published public place geometry only; selected scoped venues only. No private scope metadata, hidden IDs, SR/zone/grant IDs or exact home location. Decisions remain service-level. |
| Snapshot | Internal `embeddedRegionalDiscovery` versioned namespace freezes explicit catalogue/order/placement/distance intent/contact modes/approved original contacts; stripped from ordinary shared and compact outputs. Unknown version fails closed. |
| New stores | `my_map_regional_discovery_documents` revisioned map-owned config; `subregion_enquiry_contact_fields` approved email/phone by SR; `regional_embed_email_grants` additional authority for Original provider email only. Replace uses the approved home-SR registry and curator intent; it does not need a provider-email grant. No global approved-field SQL/claim-stage changes. |

The owner GET returns `{revision,config,options:{subregions,serviceOptions,contactAvailability}}`; options expose authorised map membership and approved-field availability, without disclosing unapproved values. Governance is initially a documented super-admin API, not a new dashboard or role. GET/PUT contact-field bodies use `{revision,status:'approved'|'withdrawn',value?,provenance,withdrawalReason?}`; Original-email grants use `{revision,status,approvedOriginalEmail?,provenance,withdrawalReason?}`. Approval binds the exact canonical email; withdrawal returns no public value. Every available email/phone URL is server-derived from its validated value.

Evaluation is bounded to 500 published entries and a 5,000ms postal lookup. The new POST alone uses existing `createRateLimiter` with name `regional-discovery-evaluate`, limit30/window60,000ms/methodsPOST; this is the existing best-effort Worker-instance limiter, not a distributed quota guarantee. Accept only `{postalCode:string}` matching `/^\d{6}$/`; reject extra fields and do not record postal/body values in analytics or request logs.

Before activation a named network steward confirms real SRs/exact nonoverlapping postal membership; each service's effective zone/assigned SR; curated public content; appropriate public distance points; and approved home-SR contact fields. The private handbook is context, not exact routing data or publication permission. Use approved metadata; no new collection/import is authorised. These are launch dependencies, not blockers for local fictional-data development. A map curator cannot grant email publication approval.
