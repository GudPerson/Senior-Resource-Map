# Care Map mobile and tablet performance exploration

The user reports sluggishness on mobile and tablet. This review accompanies the approved increase to 20,000 stored annotation points; it does not introduce a renderer, map-surface or interaction change.

## Evidence and limits

- Read-only desktop observation of the reported map `/my-directory/maps/355` found 12 imported boundaries using 1,628 stored points, one resource, 15 SVG elements, 17 paths and 13 markers. At displayed zoom 16.1, Detailed showed eight fixed image chunks and zero live tiles.
- Those eight images were 1,920 pixels high and 1,878–1,920 pixels wide. Their combined uncompressed RGBA bitmap estimate is 111.9 MiB. This is a dimensions-based estimate, not measured process memory or GPU usage. A mobile/tablet viewport can select a different number of chunks.
- Controlled real-component browser checks accepted 50 polygons with 200 exact corners each: 20,000 stored points. One atomic import, server validation, save, Undo/Redo, reload, over-budget refusal and owner PNG/PDF downloads passed. All writes used fictional persistence and all export tiles were synthetic.
- Four controlled panning profiles used 390 × 844 and 820 × 1,180 viewports with a 4× CPU slowdown, comparing five polygons against 50. Every run confirmed actual map movement. Median frame gaps were about 16.6–16.7 ms and p95 gaps 18.2–18.5 ms, with no observed long tasks in these short runs. Fifty polygons produced 51 SVG elements and 320 map DOM nodes, versus six SVG elements and 50 nodes for five polygons.
- These profiles use a bare Leaflet map with actual annotation components. They exclude the production Detailed imagery, resources, whole-page state and physical-device GPU/memory behaviour. They do not reproduce or disprove the user's reported sluggishness, establish INP/Core Web Vitals, or demonstrate a production speed improvement.
- Initial measurements clicked the mobile toolbar rather than exercising the map; they are invalid performance evidence. A later selection-profile attempt timed out. Both are retained separately. Only the four corrected browse profiles above are accepted performance observations.

## Candidates for a separate focused improvement

1. **Measure Detailed versus Standard on the user's mobile/tablet first.** The observed high-resolution bitmap workload makes image decoding/compositing a plausible contributor. Capture panning/zooming plus memory/task profiles on the actual devices before changing the locked image surfaces, memory ceiling or detail thresholds.
2. **Reduce redundant work during panning.** `DirectoryMapFixedTownViewportSync` at `client/src/components/DirectoryMap.jsx:2366-2427` emits a new bounds array on animation frames for move/zoom/resize; `handleFixedTownSurfaceViewportBoundsChange` at lines 2958-2961 updates component state and forwards it. Investigate whether chunk membership can remain stable while map movement stays in Leaflet, so unrelated UI avoids repeated work. Preserve real-time eligibility, surface-boundary fallback, resize containment and zero-live-tile proofs.
3. **Reuse unchanged annotation rendering.** `PrintAnnotationLayer` at `client/src/components/PrintAnnotationLayer.jsx:945-1073` creates a separate pane for every annotation. `AnnotationShape` at lines 418-599 constructs path options and handlers, and shape labels use DOM marker icons. Compare stable style/icon references and isolated annotation updates before considering a renderer replacement. The measured SVG/node counts show growing rendering structure; time savings are not yet measured.
4. **Profile detailed-boundary editing separately.** A selected 200-corner polygon can mount 200 draggable 44-pixel vertex markers (`AnnotationVertexHandles`, lines 247-367). Consider fewer simultaneously displayed handles or an explicit point-edit mode only if device traces show that editing causes the slowdown. Protect exact geometry, keyboard/touch targets, Move/Rotate and one-step Undo behaviour.

The first recommended next step is a device comparison of Detailed versus Standard, followed by one measured rendering optimisation. Preserve sharp imported corners, visibility, privacy, hover/focus/touch effects, existing hand-drawn shapes and owner export fidelity. Do not simplify source coordinates, change map thresholds or replace SVG with Canvas as an incidental part of increasing capacity.
